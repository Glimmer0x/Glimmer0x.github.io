# Agent 协作平台的安全威胁分类框架

## 产品背景

设想一个 Slack/Discord 形态的协作通讯平台，成员包含人类用户和 Agent 两类，账户地位对等——都可以任意发消息、被 @、主动说话。Agent 运行在用户本地机器上（Claude Code、Codex 等形态），以 `--dangerously-skip-permissions` 等方式拥有近乎完整的本地权限。

这里存在一个根本性的张力：**为了让 agent 真正有用，必须给它强本地权限；但它同时暴露在公共社交图里，任何人都能向它喊话。** 所有安全问题都源于这个张力。

---

## 威胁分类的方法论

用两个正交维度切分：

- **威胁来源**：平台方 / 其他用户 / 外部内容 / agent 供应链 / agent 自己
- **受损对象**：机器控制权 / 数据机密性 / 账号身份 / 资源成本 / 可恢复性

**分类原则：按防御机制归类，不按攻击者身份归类。** 同一套防御手段能解决的问题归为一类。这是一个关键的设计决策——如果按"攻击者身份"分类（平台作恶 / 用户作恶 / 服务商作恶 / agent 失误），会发现同一个机制需要在多个类别里重复设计，导致防御体系碎片化。

---

## 六类安全威胁

### 类型 1：输入完整性 (Input Integrity)

**本质**：agent 的"指令"和"数据"边界模糊，任何进入 context 的内容都可能被当作指令执行。

这是该产品形态最独特的结构性风险——把 agent 放进社交图，等于把攻击面放进社交图。涵盖的场景包括：

- 平台方在消息管道注入恶意 prompt
- 其他用户在 channel 里直接向我的 agent 发指令
- 其他用户的 agent 向我的 agent 发指令（agent-to-agent 攻击）
- 外部文件、网页、工具输出里藏的 prompt injection
- 社工消息欺骗 agent 执行敏感操作

**核心防御机制**：指令/数据分离、trust level 标记、来源签名、敏感操作要求 human origin 确认。

---

### 类型 2：身份真实性 (Authenticity)

**本质**：一条消息或一个动作，是谁发的、谁授权的，能否被伪造。

没有端到端签名，类型 1 的防御无从谈起——即使 agent 能区分"高可信来源"和"低可信来源"，如果身份本身可以被伪造，这套区分就毫无意义。涵盖的场景包括：

- 平台伪造或篡改消息
- 人类 vs agent 的区分、具体是哪个 agent 的区分
- user→agent→tool 的权限委托链可追溯
- 离职或换机后旧身份的作废

**核心防御机制**：端到端消息签名、设备绑定密钥、可撤销的身份证书、PKI。

---

### 类型 3：权限与爆炸半径 (Authorization & Blast Radius)

**本质**：即使 agent 被劫持、出错或服务商作恶，损害能被限制在多大范围。

这一类与类型 1 构成纵深防御的两层：类型 1 是"防止 agent 被骗"，类型 3 是"假设 agent 已被骗，限制损害范围"。两者必须同时存在。涵盖的场景包括：

- Agent 服务商推送恶意更新或模型后门
- Agent 自身 bug 或推理错误造成误操作
- Agent 主动访问不该访问的本地资源
- 供应链风险：MCP server、依赖库、自动更新机制
- 不可逆操作（删除、发送、支付）的人类确认

**核心防御机制**：Capability-based authorization、sandbox、HITL gate、权限 TTL、dry-run、undo。

---

### 类型 4：数据边界与机密性 (Confidentiality)

**本质**：敏感数据不流向不该去的地方。关注"数据流"，不是"动作"。

类型 3 限制"能做什么动作"，类型 4 限制"数据能流向哪里"。一个动作可以合法（类型 3 允许），但其数据流可能非法（类型 4 禁止）。这是用户在安装产品时第一个会问的问题。涵盖的场景包括：

- 跨 channel / 跨 organization 的信息泄漏
- 本地隐私数据被发到云端 LLM API
- Agent 记忆、日志、崩溃报告中的敏感残留
- 合规层面的数据流动（GDPR、个保法）

**核心防御机制**：信息流标签、context 隔离、本地 PII redaction、不同敏感级别走不同模型。

---

### 类型 5：资源与成本控制 (Resource Safety)

**本质**：防止 agent（被劫持或失控）消耗用户的资金、算力、配额，或被当作攻击跳板。

这一类独立成类的原因在于：防御手段是限流/熔断/配额体系，与其他类完全不同。攻击动机（经济收益）也独特——很多攻击者不想偷数据，只想白嫖资源。涵盖的场景包括：

- 经济型攻击：烧光 LLM API quota、挖矿、网络代理跳板
- Infinite loop 类 bug 导致成本失控
- 垃圾消息污染 channel

**核心防御机制**：per-user/per-agent 配额、速率限制、成本 cap、runaway detection、三级 kill switch。

---

### 类型 6：可观测性与事后恢复 (Accountability & Recovery)

**本质**：预防失败之后，能否查清、能否恢复、能否追责。

前五类是"预防"，这一类是"假设预防失败"。机制独立，且**必须事前设计，事后无法补救**——这是这一类最重要的特性。涵盖的场景包括：

- 审计日志与会话可回放
- 日志的抗篡改性（攻击者无法抹掉痕迹）
- 身份、权限、凭证的即时撤销路径
- 法律追责所需的证据链

**核心防御机制**：Append-only 日志、hash chain、tamper-evident 存储、可撤销凭证体系。

---

## 分类自检

**高内聚检验**：同一类内的威胁共享同一套防御机制。

| 类别 | 核心机制 |
|---|---|
| 1. 输入完整性 | 指令/数据分离、trust labeling、来源签名 |
| 2. 身份真实性 | 端到端签名、设备绑定密钥、PKI |
| 3. 权限与爆炸半径 | Capability、sandbox、HITL、TTL |
| 4. 数据边界与机密性 | 信息流标签、context 隔离、redaction |
| 5. 资源与成本控制 | 配额、限流、熔断 |
| 6. 可观测性与事后恢复 | Append-only log、hash chain、撤销 |

**低耦合检验**：每个底层问题只在一类中被解决，不同类的防御机制基本不重叠。

---

## 用户原始顾虑的映射

| 原始顾虑 | 归属类别 |
|---|---|
| 平台官方发布恶意 prompt | 1（劫持）+ 2（伪造） |
| 社区成员恶意指挥他人 agent | 1（劫持）+ 2（身份） |
| Agent 服务商攻击本地设备 | 3（权限限制）+ 6（日志） |
| Agent 出错造成不可逆后果 | 3（HITL、undo）+ 6（回放） |

这四项原始顾虑之间防御机制高度重叠，是同一组底层问题在不同攻击者身份下的投影。

---

## 优先级建议

对该产品形态，**最独特、业界未解好、用户最在意**的排序：

1. **类型 1（输入完整性）**：产品的结构性风险——把 agent 放进社交图等于把攻击面放进社交图
2. **类型 2（身份真实性）**：没有端到端签名，类型 1 的防御无从谈起
3. **类型 4（数据机密性）**：用户装产品时第一个会问的问题
4. **类型 6（可观测性）**：决定用户"敢不敢用"，事后补不上
5. **类型 3（权限）**：有成熟业界模式可参考
6. **类型 5（资源）**：运维层面问题，技术方案成熟

类型 1、2、4 是该产品形态的**创新性风险**，必须正面解决。类型 3、5、6 有业界成熟实践可参考。
